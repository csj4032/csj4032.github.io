전략 패턴(Strategy Pattern)은 행동(Behavioral) 디자인 패턴 중 하나로, **알고리즘 군**을 정의하고, 이를 캡슐화하여 서로 교환 가능하게 만드는 패턴입니다. 즉, 실행 중에 알고리즘을 선택할 수 있게 하며, 클라이언트 코드에 영향을 주지 않고 알고리즘을 쉽게 교체할 수 있도록 합니다.

## "상황에 따른 선택, 유연함의 미덕."

전략 패턴(Strategy Pattern)은 다음과 같은 상황에서 유용하게 사용될 수 있습니다:

  1. **여러 가지 알고리즘이 존재하고, 이들 중 하나를 런타임에 선택해야 할 때**:
    * 시스템에서 동일한 작업을 수행할 수 있는 여러 알고리즘이 존재하며, 클라이언트가 실행 중에 알고리즘을 선택하고 변경해야 할 때 유용하다. 텍스트 편집기에서 다양한 철자 검사 알고리즘(예: 영어, 프랑스어, 독일어)을 사용하여 입력된 텍스트를 검사하는 경우, 사용자는 현재 입력하는 언어에 따라 철자 검사 알고리즘을 선택할 수 있어야 한다.
  2. **알고리즘이 자주 변경되거나 확장될 가능성이 있을 때**:
    * 알고리즘이 자주 변경되거나 새로운 알고리즘이 추가될 가능성이 있는 경우, 전략 패턴을 사용하면 기존 코드에 영향을 주지 않고 쉽게 알고리즘을 변경하거나 추가할 수 있다. 결제 시스템에서 신용카드, 페이팔, 암호화폐 등 다양한 결제 방법을 지원해야 하는 경우, 새로운 결제 방법이 추가될 때 기존 코드에 영향을 주지 않고 새로운 전략을 추가할 수 있다.
  3. **알고리즘을 사용하는 클라이언트 코드와 알고리즘의 구현을 분리하고 싶을 때**:
    * 클라이언트 코드와 알고리즘의 구현을 분리함으로써 코드의 복잡성을 줄이고, 알고리즘의 구현을 독립적으로 관리할 수 있다. 이는 코드의 유지보수성과 확장성을 높이는 데 기여합니다. 데이터 분석 시스템에서 다양한 정렬 알고리즘(삽입 정렬, 퀵소트, 병합 정렬)을 사용하여 데이터를 정렬하는 경우, 클라이언트는 정렬 알고리즘의 세부 구현을 알 필요 없이 단순히 정렬 전략을 선택하여 사용할 수 있다.
  4. **조건문이나 분기문으로 알고리즘을 선택하는 코드가 복잡해질 때**:
    * 여러 알고리즘을 조건문이나 분기문을 통해 선택하는 코드가 복잡해질 경우, 전략 패턴을 사용하여 각 알고리즘을 별도의 클래스로 캡슐화하고, 클라이언트가 이를 선택하도록 할 수 있다. 이는 코드의 가독성을 높이고, 유지보수를 쉽게 만듭니다. 계산기 프로그램에서 덧셈, 뺄셈, 곱셈, 나눗셈 등 다양한 연산을 처리해야 할 때, 각 연산을 전략으로 캡슐화하여 분기문 없이 연산을 처리할 수 있다.
  5. **클라이언트 코드가 알고리즘의 변형에 영향을 받지 않도록 하고 싶을 때**:
    * 알고리즘이 자주 변형되거나 교체될 가능성이 높은 경우, 전략 패턴을 사용하여 알고리즘의 변형이 클라이언트 코드에 영향을 미치지 않도록 할 수 있다. 이는 클라이언트 코드의 안정성을 유지하는 데 도움이 된다. 게임 개발에서 캐릭터의 움직임을 제어하는 여러 알고리즘(예: 걷기, 뛰기, 점프)이 자주 변경되는 경우, 각 움직임을 전략으로 구현하여 클라이언트 코드에 영향을 주지 않고 쉽게 변경할 수 있다.

## 장점

  1. **알고리즘의 교체 용이성**
    * 전략 패턴을 사용하면 알고리즘을 런타임에 쉽게 교체할 수 있다. 클라이언트는 알고리즘의 세부 구현에 의존하지 않고, 필요에 따라 다른 알고리즘을 선택할 수 있다. 결제 시스템에서 결제 방법(신용카드, 페이팔, 암호화폐 등)을 쉽게 교체할 수 있다. 새로운 결제 방법을 추가하더라도 기존 코드에 영향을 주지 않고 전략을 교체할 수 있다.
  2. **클라이언트 코드의 복잡성 감소**
    * 알고리즘의 선택과 구현을 별도의 클래스로 분리함으로써, 클라이언트 코드가 알고리즘의 세부 사항에 관여할 필요가 없다. 클라이언트는 전략을 선택하고 사용할 수 있을 뿐, 알고리즘의 내부 동작을 알 필요가 없다. 데이터 분석 시스템에서 다양한 정렬 알고리즘을 사용할 때, 클라이언트는 단순히 원하는 정렬 전략을 설정하고 데이터를 정렬할 수 있다.
  3. **조건문이나 분기문의 제거**
    * 여러 알고리즘을 선택하는 조건문이나 분기문을 사용하지 않고, 각 알고리즘을 별도의 클래스로 캡슐화할 수 있다. 이를 통해 코드의 가독성과 유지보수성을 높일 수 있다. 게임 캐릭터의 움직임(걷기, 뛰기, 점프 등)을 처리하는 코드에서, 각각의 움직임을 조건문으로 처리하는 대신 전략 패턴을 사용하여 조건문을 제거하고 각 움직임을 캡슐화할 수 있다.
  4. **OCP(Open/Closed Principle) 준수**
    * 전략 패턴은 OCP(개방-폐쇄 원칙)를 준수하여, 기존 코드를 수정하지 않고도 새로운 알고리즘을 추가할 수 있게 한다. 기존 알고리즘을 수정하지 않고도 새로운 전략 클래스를 추가할 수 있다. 텍스트 편집기에서 새로운 철자 검사 알고리즘을 추가할 때, 기존의 철자 검사 클래스에 영향을 주지 않고 새로운 전략 클래스를 추가할 수 있다.
  5. **유연성과 확장성 제공**
    * 알고리즘을 클래스로 분리하고 인터페이스를 통해 접근함으로써, 시스템이 유연하고 확장 가능하다. 새로운 전략을 추가하거나 기존 전략을 교체하는 작업이 매우 간단해진다. 주식 거래 시스템에서 다양한 매매 전략(예: 단기 매매, 장기 매매)을 쉽게 추가하거나 교체할 수 있다.

## 단점

  1. **클래스 수 증가**
    * 전략 패턴을 사용하면 각 알고리즘을 별도의 클래스에 캡슐화해야 하므로, 알고리즘의 수가 많아질수록 클래스의 수가 급격히 증가한다. 이는 코드베이스를 복잡하게 만들고, 관리해야 할 클래스가 많아져 유지보수가 어려워질 수 있다. 다양한 결제 방법을 지원하는 시스템에서, 각 결제 방법마다 별도의 전략 클래스를 만들어야 하므로, 결제 방법이 많아질수록 클래스의 수가 증가하게 된다.
  2. **클라이언트의 전략 선택 책임**
    * 전략 패턴을 사용할 때, 클라이언트는 상황에 맞는 적절한 전략을 선택해야 한다. 이는 클라이언트가 전략 패턴의 사용법을 정확히 이해하고 있어야 하며, 적절한 전략을 선택하는 책임이 클라이언트에게 있다는 것을 의미한다. 데이터 처리 시스템에서 클라이언트가 잘못된 정렬 전략을 선택하면, 데이터 처리 결과가 예상과 다르게 나올 수 있다.
  3. **알고리즘 간의 차이점이 클 경우 어려움**
    * 전략 패턴은 여러 알고리즘이 동일한 인터페이스를 공유해야 하는데, 알고리즘 간에 차이점이 클 경우 동일한 인터페이스로 묶는 것이 어려울 수 있다. 이로 인해 인터페이스가 지나치게 복잡해질 수 있다. 주식 거래 시스템에서 매매 전략이 매우 달라서 동일한 인터페이스로 묶기 어려운 경우, 각 전략을 구현하는 데 복잡성이 증가할 수 있다.
  4. **캡슐화의 부족**
    * 전략 패턴을 사용하면 알고리즘이 구체적인 전략 클래스로 분리되지만, 클라이언트 코드에서 전략을 설정하고 호출해야 하므로 완전한 캡슐화가 이루어지지 않을 수 있다. 클라이언트가 전략의 내부 동작을 이해하고 있어야 하는 경우가 발생할 수 있다. 클라이언트가 특정 전략을 사용할 때 그 전략의 부작용을 알지 못하면, 예상치 못한 결과가 발생할 수 있다.
  5. **알고리즘의 캡슐화 부족으로 인한 중복 가능성**
    * 각 전략 클래스에서 알고리즘을 별도로 구현하다 보면, 일부 코드가 중복될 가능성이 있다. 특히 알고리즘의 큰 부분이 유사한 경우, 코드 중복이 발생하여 유지보수가 어려워질 수 있습니다. 여러 정렬 알고리즘이 유사한 방식으로 동작하지만, 세부적인 부분만 다른 경우 코드 중복이 발생할 수 있다.

전략 패턴(Strategy Pattern)을 사용한 예제: 텍스트 정렬기:

이 예제에서는 텍스트 정렬기를 만들 것입니다. 텍스트 정렬기는 주어진 문자열 배열을 정렬하는 기능을 제공, 다양한 정렬 알고리즘(예: 알파벳순, 길이순 등)을 전략 패턴을 사용해 구현

```java
// 전략 인터페이스
interface SortStrategy {
    void sort(String[] items);
}

// 구체적인 전략 클래스 1: 알파벳순 정렬
class AlphabeticalSort implements SortStrategy {
    @Override
    public void sort(String[] items) {
        Arrays.sort(items);
        System.out.println("Sorted alphabetically: " + Arrays.toString(items));
    }
}

// 구체적인 전략 클래스 2: 문자열 길이순 정렬
class LengthSort implements SortStrategy {
    @Override
    public void sort(String[] items) {
        Arrays.sort(items, Comparator.comparingInt(String::length));
        System.out.println("Sorted by length: " + Arrays.toString(items));
    }
}

// 컨텍스트 클래스
class TextSorter {
    private SortStrategy strategy;

    // 정렬 전략 설정 메서드
    public void setStrategy(SortStrategy strategy) {
        this.strategy = strategy;
    }

    // 정렬 실행 메서드
    public void sortText(String[] items) {
        if (strategy == null) {
            throw new IllegalStateException("Sort strategy not set.");
        }
        strategy.sort(items);
    }
}

// 클라이언트 코드
public class StrategyPatternExample {
    public static void main(String[] args) {
        // 정렬할 텍스트 배열
        String[] text = {"apple", "banana", "kiwi", "cherry", "orange"};

        // 컨텍스트 클래스 생성
        TextSorter sorter = new TextSorter();

        // 알파벳순 정렬 전략 설정
        sorter.setStrategy(new AlphabeticalSort());
        sorter.sortText(text);

        // 문자열 길이순 정렬 전략 설정
        sorter.setStrategy(new LengthSort());
        sorter.sortText(text);
    }
}
```

## 코드 설명

  1. **SortStrategy 인터페이스 (전략 인터페이스)**:
    * SortStrategy 인터페이스는 sort(String[] items) 메서드를 정의하여, 문자열 배열을 정렬하는 알고리즘의 공통 인터페이스를 제공
  2. **AlphabeticalSort, LengthSort 클래스 (구체적인 전략)**:
    * AlphabeticalSort 클래스는 문자열을 알파벳순으로 정렬하는 알고리즘을 구현
    * LengthSort 클래스는 문자열을 길이순으로 정렬하는 알고리즘을 구현
  3. **TextSorter 클래스 (컨텍스트 클래스)**:
    * TextSorter 클래스는 정렬 전략을 설정하고, 설정된 전략에 따라 문자열 배열을 정렬하는 역할
    * setStrategy(SortStrategy strategy) 메서드를 통해 정렬 전략을 설정하고, sortText(String[] items) 메서드를 통해 정렬을 실행
  4. **클라이언트 코드**:
    * 클라이언트는 TextSorter 객체를 생성하고, setStrategy() 메서드를 사용해 원하는 정렬 전략을 설정
    * 설정된 전략에 따라 sortText() 메서드를 호출해 문자열 배열을 정렬

## 관련 패턴

  1. **템플릿 메서드(Template Method) 패턴**
    * 템플릿 메서드 패턴은 알고리즘의 구조를 정의하고, 알고리즘의 일부 단계를 서브클래스에서 구현하도록 하는 패턴입니다. 전략 패턴과 템플릿 메서드 패턴은 알고리즘의 변형 가능성을 제공한다는 점에서 유사합니다. 전략 패턴은 알고리즘을 외부에서 설정할 수 있는 인터페이스로 분리하고, 템플릿 메서드 패턴은 알고리즘의 구조를 상위 클래스에서 정의하며 하위 클래스에서 일부 단계를 재정의할 수 있도록 합니다.
  2. **상태(State) 패턴**
    * 상태 패턴은 객체의 상태에 따라 행동을 변경할 수 있도록 하는 패턴이다. 전략 패턴과 상태 패턴은 모두 행동을 캡슐화하여 객체가 동일한 메서드를 호출할 때도 다른 결과를 제공할 수 있다는 점에서 유사하다. 전략 패턴은 주로 알고리즘의 교체에 초점을 맞추고, 상태 패턴은 객체의 상태 변화에 따라 다른 행동을 하도록 설계된다.
  3. **팩토리 메서드(Factory Method) 패턴**
    * 팩토리 메서드 패턴은 객체 생성을 캡슐화하여 클라이언트 코드와 객체 생성 로직을 분리하는 패턴이다. 전략 패턴과 함께 사용될 때, 팩토리 메서드 패턴은 전략 객체를 생성하는 역할을 할 수 있다. 클라이언트는 팩토리 메서드를 통해 생성된 전략 객체를 받아 사용하며, 이렇게 함으로써 전략 객체의 생성 로직을 캡슐화할 수 있다.
  4. **디코레이터(Decorator) 패턴**
    * 디코레이터 패턴은 객체에 새로운 기능을 동적으로 추가할 수 있게 하는 패턴이다. 전략 패턴과 디코레이터 패턴은 객체의 행동을 변경할 수 있다는 점에서 유사하다. 전략 패턴은 알고리즘 자체를 교체하는 데 중점을 두는 반면, 디코레이터 패턴은 기존 객체에 추가적인 기능을 덧붙이는 데 중점을 둔다.
  5. **커맨드(Command) 패턴**
    * 커맨드 패턴은 요청을 객체로 캡슐화하여, 클라이언트가 요청을 수행할 수 있도록 하는 패턴이다. 전략 패턴과 커맨드 패턴은 모두 행동을 캡슐화하여 클라이언트가 행동의 세부 사항을 알 필요 없이 요청을 실행할 수 있다는 점에서 유사하다. 전략 패턴은 알고리즘의 선택과 실행에 중점을 두고, 커맨드 패턴은 요청의 캡슐화와 실행에 중점을 둔다.
  6. **브리지(Bridge) 패턴**
    * 브리지 패턴은 추상화와 구현을 분리하여, 이들이 독립적으로 변형될 수 있도록 하는 패턴이다. 전략 패턴과 브리지 패턴은 모두 객체의 행위를 동적으로 변경하거나 교체할 수 있다는 점에서 유사하다. 전략 패턴은 알고리즘을 외부에서 설정할 수 있는 인터페이스로 분리하고, 브리지 패턴은 추상화와 구현을 별도로 관리하여 독립적인 변경을 가능하게 한다.
  7. **의존성 주입(Dependency Injection)**
    * 의존성 주입은 객체 간의 의존성을 외부에서 주입하여 객체의 생성과 사용을 분리하는 기법이다. 전략 패턴과 함께 사용될 때, 의존성 주입은 전략 객체를 클라이언트에 주입하는 역할을 할 수 있다. 이를 통해 전략 패턴의 유연성을 높이고, 클라이언트가 전략 객체의 생성과 관리를 신경 쓰지 않도록 할 수 있다.
